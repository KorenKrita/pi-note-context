# Design review request: `pi-note-context` — a notebook-backed context-window plugin for the Pi coding agent

You are reviewing a design before implementation. Be direct. Point out flaws, missing cases, and places where the design will fail with real models. Answer the numbered questions at the end explicitly, one by one. Do not soften.

## Host facts (Pi 0.85.1, verified from source)

- Extensions hook a `context` event that runs before **every** LLM call with a deep copy of the message array; the handler may return a replacement array. Nothing returned here is persisted.
- Extensions persist data with `appendEntry(customType, data)` into the session journal (a tree of entries; `/tree` can move the leaf). Custom entries never enter LLM context.
- Extensions can inject a persisted message with `sendMessage({customType, content}, {deliverAs: "steer"})` — delivered after the current turn's tool calls finish, before the next LLM call.
- Compaction: when context exceeds `contextWindow - reserveTokens`, Pi fires `session_before_compact` with a `preparation` (cut point `firstKeptEntryId` chosen to keep ~`keepRecentTokens` of recent turns intact). An extension may return `{compaction: {summary, firstKeptEntryId, tokensBefore}}` to replace the LLM summary with its own text. After compaction the model sees: compaction summary message + entries from `firstKeptEntryId` onward. Extensions can also trigger compaction via `ctx.compact()`.
- Multiple extensions: the **last** non-empty result wins. Another installed extension (`pi-codex-ws-compaction`) claims compaction only for specific OpenAI Responses models (remote encrypted compaction). For those models this plugin will yield the compaction step to it but still inject notes, remind, and serve history.
- `ctx.getContextUsage()` gives `{tokens, contextWindow, percent}`; `tokens` is null right after compaction until the next response.

## Prior art examined

- **oh-my-pi** `experimentalContextManagement`: single `context_notes` file (16 KiB, whole-text replace), `new_context` tool (zero args, flag → rollover at next safe boundary, no LLM summary, keeps recent tail + notebook + latest user request), `history://current/full` readable via read/grep. One reminder per window when near threshold. Notebook header tells the model to treat notes as "untrusted historical data until verified." Default off.
- **Codex CLI** `features.context_management.experimental_mode` (PR #42385, 2026-09-02): server-side `notes.*` (multi-file, append/write/read/search, 1 MB/file) and `history.*` (list_windows/list_items/read_item/search_contents), `new_context` tool, `get_context_remaining` tool. Every non-assistant item carries a trailing `[id: …]`. Model-catalog guidance (gpt-5.6-*/gpt-6-astra): "take incremental notes while you work"; reminder at 6144 tokens remaining; when exhausted, a 16384-token fallback buffer with "make exactly one notes write, then call new_context, use no other tools." Notes/history are "private model-only state; never disclose to the user." Known issue #43194: notes backend 404 yet `new_context` still allowed → state lost.

## Proposed design

### Tools (model-invoked, no prefix)

1. `notes` — sectioned notebook, **one notebook per session branch**, 8 KiB total cap, injected on every LLM call.
   - `notes()` read whole; `notes({section, text})` replace one section (create if absent); `notes({section, text: ""})` delete section; `notes({text})` rewrite whole (escape hatch).
   - Suggested section names in the tool description: Goal / Constraints / Done / Now / Next / Decisions / Ruled-out / Pointers / Open.
   - Rationale vs. omp whole-replace: cheaper incremental writes, no accidental line loss when rewriting a long text. Vs. Codex append/multi-file: notes are injected so they must stay small and pruned; per-section replace keeps pruning pressure.
2. `new_context` — zero args. Sets a flag; at the next safe boundary the plugin runs a **no-LLM rollover** (compaction with a fixed template summary). Freshness gate: refused if no `notes` write has happened in the current window ("update notes first").
3. `history` — `history({query, window?})` literal substring search over the current branch's full journal (including pre-rollover entries) and `history({id})` to read one entry. Every tool result gets a trailing `[id: xxxx]` so notes can point precisely.

### Injection (every LLM call, appended at the tail, just before the latest user message)

```
window 142K/272K · notes: 3 turns ago · window #2 (prev #1)
<notebook sections…>
```
Facts only. When within ~20K tokens of the compaction threshold, one extra line per window: "rollover threshold in ~18K tokens — refresh notes, then new_context when they are current." Tail placement: prompt-cache-friendly and keeps goal/state in the recent-attention window (Manus todo.md recitation effect).

### Safety net (model did not call new_context)

Two-stage, borrowing Codex: at threshold, first steer a developer message "make exactly one notes write now, then call new_context; use no other tools", allowing one more turn; then rollover. Rollover summary is a fixed template: "Context window #N started. Earlier raw transcript stays searchable via `history`. Continue from notes (below) and the retained recent tail. The latest user request is preserved separately when it fell outside the tail."

### Guidance to the model (system prompt section, imperative)

- When to write notes: the moment you make a decision, change a file, rule out a direction, obtain a key value, or see the threshold line. One line per item; replace stale entries.
- **When to call `new_context`** — the raw material in this window has no further use and everything worth keeping is in notes. Typical moments: exploration concluded; a self-contained unit finished (committed/tested/reported); a large one-off output (logs, diffs, test runs) read and its conclusion recorded; a direction abandoned with the reason recorded; the user switched to an unrelated request. **Do not** when mid-edit, with unprocessed tool results, with fresh information not yet in notes, or with the user's last question unanswered. Single test: "If I switch now, what would I need `history` for in the next three steps?" — nothing, or one or two known ids → switch; a vague list → write notes first or keep working.
- After a rollover: continue from notes and the retained tail; use `history` for missing detail.

### Observability

Local append-only ledger: notes writes per window, freshness at rollover, `history` calls in the first 5 turns after rollover, whether rollover was model-initiated or safety-net.

## Questions — answer each explicitly

1. Is per-section replace the right write primitive, or will models fight it (e.g., dumping everything into one section, inventing section names every turn)? Would you prefer whole-replace (omp) or append (Codex)? Why?
2. 8 KiB injected every call: too small, too large, or fine? How should the cap interact with the model's tendency to hoard?
3. Tail injection just before the latest user message: any failure mode with reasoning models or with tool-call/tool-result pairing that must stay adjacent?
4. The freshness gate on `new_context` (refuse if no notes write this window): good safety or an annoying loop? What exactly should "fresh" mean?
5. Is the proposed "when to call new_context" guidance actually actionable for a model like you? What would make you call it too often, too rarely, or at the wrong moment? Rewrite the guidance in your own words if you think it should be different.
6. Two-stage safety net (one-more-turn note write, then rollover): does the "exactly one notes write, no other tools" constraint work in practice, or do models ignore it?
7. Codex says notes/history are private model-only state, never disclosed to the user. We plan to make the notebook user-visible in the TUI. Any downside for model behavior?
8. Codex tells the model to treat nothing as untrusted; omp tells the model notes are "untrusted historical data until verified". We plan to say neither. Which stance produces better behavior after a rollover — trust your own notes, or re-verify?
9. `[id: xxxx]` trailer on every tool result: worth the tokens? Any better addressing scheme?
10. What is missing from this design that you would insist on before shipping?
